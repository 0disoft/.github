# 安全政策

语言: [English](../../../SECURITY.md) | [한국어](../ko/SECURITY.md) | [Español](../es/SECURITY.md) | [Français](../fr/SECURITY.md) | [हिन्दी](../hi/SECURITY.md) | 简体中文

这是适用于 0disoft 所有仓库的默认安全政策。如果某个仓库有自己的 `SECURITY.md`，则以该仓库的专用安全政策为准。

## 支持的仓库

安全报告主要针对仍在积极维护的仓库进行审查。

已归档、实验性、已弃用或不再维护的仓库，可能不会收到安全修复。

除非仓库另有说明，安全相关工作会在力所能及的范围内处理，默认面向默认分支以及最新公开版本；如果该仓库使用 releases，则以最新公开 release 为准。

## 对贡献的安全要求

如果某项改动新增或修改了身份认证、权限控制、密码学、密钥处理、支付处理、个人数据处理，或会暴露在网络上的行为，则需要维护者进行额外审查。

## 密码学政策

对于任何新增、修改或依赖密码学行为的改动：

- 不要在没有维护者明确批准和适当安全审查的情况下，自行实现密码学方案，或直接组合密码学原语。
- 优先使用成熟的协议、维护良好的库，以及处于标准化流程中的实现。
- 对称密码和哈希函数仍然可以使用。请通过维护良好的库使用现代的认证加密、消息认证和哈希原语。
- 在可行的情况下，密码学选择应当可以配置、可以替换。如果协议协商或库配置已经可用，应避免把算法直接硬编码到代码中。

### 公钥密码学与后量子密码学

- 对于新的公钥加密、密钥建立或数字签名功能，在已有可用于生产环境的支持时，应优先选择 NIST 标准化的后量子密码学方案。
- 新的密钥建立功能优先考虑 ML-KEM。新的数字签名功能在符合协议和运行环境的情况下，优先考虑 ML-DSA 或 SLH-DSA。
- 持续关注其他 NIST 标准化或处于标准化流程中的算法，包括 FN-DSA 和 HQC，并根据其成熟度再决定是否采用。
- 在互操作性需要时，可以使用传统密码学与后量子密码学的混合配置，但前提是遵循公认的协议、配置文件，或供应商支持的标准。
- 为了兼容性，现有的 RSA、Diffie-Hellman、ECDH、ECDSA 或 EdDSA 使用可以保留。但新的长期密钥、长期信任根，以及新的密码协议设计，在可行的情况下应当具备后量子迁移能力。
- 未经维护者明确批准和安全审查，不要在生产代码中使用非标准、实验性或仅限研究用途的后量子密码学方案。

目标不是立即禁止所有现有密码学。目标是避免新增不必要的、容易受到量子计算威胁的公钥依赖，并让密码学组件保持可替换。

## 密码存储政策

如果项目存储用户密码：

- 不要以明文形式存储密码，也不要使用可逆加密方式存储密码。
- 不要直接使用 MD5、SHA-1、SHA-256 或 SHA-512 这类快速通用哈希函数来处理密码。
- 新的密码哈希应优先使用 Argon2id。
- 每个密码都应使用唯一、随机生成的盐值（salt）。对于 Argon2id 密码哈希，建议使用 16 字节盐值。
- 在可行的情况下，使用维护良好的库和标准密码哈希格式。
- Argon2id 参数应当可以配置，并随着硬件性能和部署环境的变化定期重新评估。
- 除非仓库专用政策定义了更严格的参数，否则至少应使用 OWASP 推荐的 Argon2id 最低基准：19 MiB 内存、2 次迭代、1 个并行度。
- 如果无法使用 Argon2id，应尽可能使用 scrypt。对于遗留系统，可以暂时保留 bcrypt，但应使用合适的工作因子并制定迁移计划。如果需要满足 FIPS-140 合规要求，则应使用 PBKDF2-HMAC-SHA-256，并配合已批准的工作因子。
- 不要使用快速哈希、无盐哈希，或自定义密码哈希方案。
- 每个密码哈希都应一并存储算法、参数、盐值和哈希版本，以便未来逐步升级。

## Token、API Key 与密钥政策

对于机器生成的 token、API key、恢复码以及类似密钥：

- 使用密码学安全的随机数生成器生成密钥。
- 不要存储原始 API key、访问 token、刷新 token、会话 token 或恢复码，除非存在明确的运行需求。
- 在不需要恢复原文的情况下，优先存储带密钥的哈希、普通哈希，或不可逆验证值。
- 密钥不得提交到仓库，不得写入日志，不得暴露在错误消息中，也不得存放在测试夹具或测试数据中。
- 运行环境中的密钥应使用密钥管理器、环境专用密钥存储，或平台提供的加密密钥功能。

## 依赖与供应链安全

- 依赖应保持在合理的新版本范围内。
- 与安全相关的依赖变更，应在 release 前进行审查。
- 未经维护者审查，不要新增用于密码学、身份认证、权限控制、序列化、模板渲染或网络解析的依赖。

## 报告漏洞

请不要通过公开 issues、pull requests 或 discussions 报告安全漏洞。

请通过 GitHub 的私密渠道报告：

1. 打开受影响的仓库，进入 **Security** 标签页，选择 **Report a vulnerability**。维护中的 0disoft 仓库已启用私有漏洞报告。
2. 如果该选项不可用，请创建一个仅请求私密联系方式的 issue，且不要在该 issue 中写入技术细节、漏洞利用步骤或受影响版本。
3. 如果无法确定受影响的仓库，或该仓库不接受私密报告，请在 `0disoft/.github` 上使用相同的 **Security** 标签页流程。该仓库是默认策略仓库，也是本账号的备用联系渠道。

报告漏洞时，请包含以下信息：

- 受影响的仓库
- 受影响的版本、分支或 commit，如果已知
- 对问题的清晰描述
- 复现问题的步骤
- 潜在影响
- 如果有可用的缓解建议，也请一并提供

## 处理方式

报告将本着善意进行审查。

维护者可能会要求提供更多细节、准备修复、协调披露流程，或判断所报告的问题并不属于安全漏洞。

在修复或缓解措施准备好之前，请避免公开披露该问题。除非维护者在不合理的长时间内没有回应。
