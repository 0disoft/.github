# Guide de contribution

Langue : [English](../../../CONTRIBUTING.md) | [한국어](../ko/CONTRIBUTING.md) | [Español](../es/CONTRIBUTING.md) | Français | [हिन्दी](../hi/CONTRIBUTING.md) | [简体中文](../zh-CN/CONTRIBUTING.md)

Merci d’envisager de contribuer à un projet 0disoft.

Ce document constitue le guide de contribution par défaut des dépôts appartenant à 0disoft. Si un dépôt possède son propre `CONTRIBUTING.md`, le guide propre à ce dépôt prévaut.

Consultez la [gouvernance](./GOVERNANCE.md) pour connaître les rôles des mainteneurs et le processus de décision.

## Avant de contribuer

Avant d’ouvrir une nouvelle issue ou une pull request, consultez d’abord le README du dépôt, les issues existantes et les pull requests déjà ouvertes.

Pour les changements plus importants, ouvrez d’abord une issue afin de discuter du périmètre et de la direction avant de commencer l’implémentation.

Pour les vulnérabilités de sécurité, n’ouvrez pas d’issue publique. Suivez plutôt les instructions de `SECURITY.md`.

## Issues

Utilisez les issues pour :

- signaler des bugs reproductibles
- proposer des fonctionnalités avec un périmètre clair
- signaler des problèmes de documentation
- poser des questions propres au projet qui pourraient aussi aider d’autres utilisateurs

Lorsque vous ouvrez une issue, incluez :

- le comportement attendu
- le comportement réellement observé
- les étapes permettant de reproduire le problème, le cas échéant
- les journaux, captures d’écran, versions ou détails d’environnement pertinents

Gardez chaque issue centrée sur un seul problème ou une seule demande.

## Pull Requests

Les pull requests sont les bienvenues lorsqu’elles sont ciblées et faciles à examiner.

Avant d’ouvrir une pull request :

- gardez le changement aussi limité que possible
- expliquez pourquoi ce changement est nécessaire
- ajoutez des tests ou de la documentation lorsque c’est pertinent
- évitez les refactorisations sans rapport avec le changement
- suivez les éventuelles instructions propres au dépôt

Une pull request peut être refusée si elle sort du périmètre du projet, si elle est trop large pour être examinée sereinement, ou si elle va à l’encontre de la direction du dépôt.

## Instructions propres au dépôt

Les commandes de build, les commandes de test, les règles de publication, les notes d’architecture, les politiques de dépendances et les instructions de déploiement doivent être documentées dans le README de chaque dépôt ou dans son `CONTRIBUTING.md` spécifique.
